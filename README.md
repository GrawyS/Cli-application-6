# depviz — визуализация графа зависимостей Maven-пакета

Практическая работа по дисциплине «Конфигурационное управление»
(РТУ МИРЭА, ИКБО-32-25), вариант 6.

## 1. Общее описание

`depviz` — консольное приложение на Python 3 (без сторонних библиотек).
Оно по координатам Maven-пакета (`groupId:artifactId`, версия) скачивает
его POM-файл, извлекает зависимости, строит полный граф с учётом
транзитивности и показывает его:

* текстом и ASCII-деревом;
* в виде диаграммы PlantUML (`.puml`) и изображения `.svg`;
* в обратном виде: какие пакеты зависят от заданного.

Менеджеры пакетов (`mvn`, Gradle) и библиотеки для получения зависимостей
не используются: POM скачивается через `urllib`, разбирается `xml.etree`.

Этапы работы и где они реализованы:

| Этап | Что сделано | Модуль |
|------|-------------|--------|
| 1 | Настройки из INI-файла, проверка всех параметров | `src/depviz/config.py` |
| 2 | Прямые зависимости из POM (формат Maven) | `src/depviz/maven.py` |
| 3 | Граф: DFS без рекурсии, глубина, циклы, тестовый режим | `graph.py`, `testrepo.py`, `repository.py` |
| 4 | Обратные зависимости (тот же DFS по инвертированному графу) | `src/depviz/reverse.py` |
| 5 | PlantUML → SVG, ASCII-дерево | `plantuml.py`, `asciitree.py` |

Структура репозитория:

```
src/depviz/   исходный код
tests/        модульные тесты (unittest)
examples/     примеры конфигураций и тестовых репозиториев
tools/        локальная проверка стиля (check_style.py)
config.ini    конфигурация по умолчанию
run.sh, run.bat, Makefile   запуск
```

## 2. Функции и настройки

### Файл настроек (INI, секция `[settings]`)

| Параметр | Описание |
|----------|----------|
| `package_name` | Имя пакета `groupId:artifactId` (в тестовом режиме — заглавные латинские буквы, например `A`) |
| `repo_url` | URL Maven-репозитория (`real`) или путь к файлу описания графа (`test`) |
| `repo_mode` | `real` — настоящий репозиторий, `test` — тестовый файл |
| `package_version` | Версия пакета, `latest` не поддерживается (в тестовом режиме не нужна) |
| `output_file` | Имя SVG-файла с графом (расширение `.svg`, каталог должен существовать) |
| `ascii_tree` | `true`/`false` — выводить ли зависимости ASCII-деревом |
| `max_depth` | Максимальная глубина анализа, целое число ≥ 1 |

Все ошибки конфигурации собираются и выводятся списком, код возврата 1.
Неизвестные параметры тоже считаются ошибкой (так ловятся опечатки).

### Опции командной строки

| Опция | Этап | Действие |
|-------|------|----------|
| `-c`, `--config ФАЙЛ` | — | INI-файл настроек (по умолчанию `config.ini`) |
| `--show-config` | 1 | Вывести настройки в формате `ключ = значение` |
| `--direct` | 2 | Вывести прямые зависимости пакета |
| *(без опций)* | 3, 5 | Построить граф, вывести его, дерево, сохранить `.puml` и `.svg` |
| `--reverse ПАКЕТ` | 4 | Вывести пакеты, зависящие от `ПАКЕТА` |
| `--puml-only` | 5 | Сохранить только `.puml`, без построения SVG |

### Как строится граф

* **Источник данных.** POM берётся по пути
  `<repo>/<group/как/путь>/<artifact>/<version>/<artifact>-<version>.pom`.
* **Какие зависимости учитываются.** Берутся `compile` и `runtime`;
  `test`, `provided`, `system`, `import` и `<optional>true</optional>`
  пропускаются.
* **Версии.** Раскрываются `${свойства}` (включая `project.version`),
  версии из `dependencyManagement` и родительских POM; для диапазона
  `[1.0,2.0)` берётся первая граница. Если версию определить нельзя,
  зависимость пропускается с предупреждением.
* **DFS без рекурсии.** Обход идёт с явным стеком, поэтому глубокие
  цепочки не вызывают `RecursionError`. Корень находится на глубине 0,
  узлы на глубине `max_depth` не раскрываются (в выводе помечены `(...)`).
  Если узел сначала встретился глубоко, а потом по более короткому пути,
  он раскрывается заново.
* **Циклы.** Узел, который уже лежит на текущем пути, не раскрывается
  повторно; ребро запоминается как «обратное» и помечается в выводе
  (`(цикл)`), на диаграмме рисуется красным пунктиром.
* **Ошибки.** Если не найден корневой пакет — ошибка и код 1. Если
  недоступен вложенный пакет, он помечается в графе, остальное строится.
* **Обратные зависимости.** Внутри построенного графа рёбра
  разворачиваются, и тот же `build_graph` обходит инвертированный граф от
  выбранного пакета. Искать зависимых вне графа (во всём репозитории)
  нельзя, поэтому результат ограничен `package_name` и `max_depth`.
  Если указать `group:artifact` без версии, обрабатываются все версии
  этого пакета в графе.
* **SVG.** Если в системе есть команда `plantuml`, используется она
  (можно задать свою через `PLANTUML_CMD`, например
  `PLANTUML_CMD="java -jar plantuml.jar"`). Иначе текст диаграммы
  кодируется и отправляется на сервер PlantUML
  (`https://www.plantuml.com/plantuml`, меняется через `PLANTUML_SERVER`).
  Файл `.puml` сохраняется всегда, даже если SVG построить не удалось.

### Тестовый режим

Вместо URL указывается файл, где пакеты названы заглавными латинскими
буквами. Формат — строка на пакет, `#` начинает комментарий:

```
A: B C
B: D
C: D E
D:
```

Пакет, который упомянут только как зависимость, считается листом.
Примеры: `examples/test_repo.txt` (ромб), `cycle.txt` (цикл),
`chain.txt` (длинная цепочка), `shortcut.txt` (короткий и длинный путь).

## 3. Сборка, запуск и тесты

Нужен только Python 3.9+ (проверялось на 3.13); сборки нет. Для SVG желательно иметь `plantuml`
или доступ к интернету.

```sh
./run.sh --show-config               # Linux/macOS
run.bat --show-config                # Windows
make run ARGS="--show-config"        # через Makefile

make test                            # запуск тестов
make check                           # проверка правил оформления кода
# без make:
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

## 4. Примеры использования

Все примеры ниже выполнены на тестовом репозитории
(`examples/test_config.ini` указывает на `examples/test_repo.txt`).

**Этап 1. Настройки**

```
$ ./run.sh -c examples/test_config.ini --show-config
package_name = A
repo_url = examples/test_repo.txt
repo_mode = test
package_version =
output_file = graph.svg
ascii_tree = True
max_depth = 5
```

Ошибки (по каждому параметру):

```
$ ./run.sh -c bad.ini
Ошибки в конфигурации:
  - package_name: 'x' не подходит: формат groupId:artifactId
  - repo_url: 'ftp://a' должен быть URL вида https://host/path
  - max_depth: значение должно быть не меньше 1
```

**Этап 2. Прямые зависимости реального пакета**

```
./run.sh -c examples/real_commons_text.ini --direct
```

**Этап 3. Граф, глубина, циклы**

```
$ ./run.sh -c examples/test_config.ini --puml-only
Узлов: 5, рёбер: 5
  A -> B, C
  B -> D
  D -> -
  C -> D, E
  E -> -
```

Цикл (`examples/cycle.txt`: A → B → C → A) завершается и помечается:

```
A
└── B
    └── C
        ├── A (цикл)
        └── D
```

Если поставить `max_depth = 2` на `examples/chain.txt`, обход остановится
на узле `C`, и в выводе появится «Глубина исчерпана, не раскрыт: C».

**Этап 4. Обратные зависимости**

```
$ ./run.sh -c examples/test_config.ini --reverse D
Обратные зависимости D:
  Прямые:
    - B
    - C
  Через другие пакеты:
    - A
```

**Этап 5. Диаграмма и изображение**

```
$ ./run.sh -c examples/test_config.ini
...
Дерево зависимостей:
A
├── B
│   └── D
└── C
    ├── D
    └── E

Диаграмма PlantUML: graph.puml
Изображение графа: graph.svg
```

Содержимое `graph.puml`:

```
@startuml
title Зависимости A
left to right direction
skinparam shadowing false
rectangle "A" as n0 #LightBlue
rectangle "B" as n1
rectangle "D" as n2
rectangle "C" as n3
rectangle "E" as n4
n0 --> n1
n0 --> n3
n1 --> n2
n3 --> n2
n3 --> n4
@enduml
```

Три пакета для демонстрации на реальном репозитории (готовые конфиги):

```
./run.sh -c examples/real_commons_text.ini   # commons-text 1.11.0
./run.sh -c examples/real_guava.ini          # guava 33.0.0-jre
./run.sh -c examples/real_jackson.ini        # jackson-databind 2.16.1
```

### Сравнение со штатным инструментом Maven

Штатный инструмент — `mvn dependency:tree`. Для сравнения нужно создать
`pom.xml` с одной зависимостью (той же версии) и выполнить
`mvn dependency:tree`. Расхождения с `depviz` ожидаются по следующим
причинам:

* Maven разрешает конфликты версий по правилу «ближайшее определение
  побеждает», `depviz` показывает версии так, как они указаны в POM, и
  один и тот же пакет может встретиться в двух версиях.
* Maven учитывает `<exclusions>` и `dependencyManagement` проекта-потребителя
  и BOM (`scope=import`); `depviz` BOM не раскрывает и exclusions не
  применяет.
* `mvn dependency:tree` по умолчанию показывает и `test`-зависимости самого
  проекта, но не транзитивные `test`/`provided`; `depviz` отбрасывает их
  везде одинаково.
* Диапазоны версий Maven разрешает по метаданным репозитория, `depviz`
  берёт первую границу диапазона.
* Maven по умолчанию не показывает повторяющиеся и проигравшие в
  конфликте узлы; `depviz` показывает такой узел один раз, а повторы
  помечает `(см. выше)`.

> Результаты сравнения на реальных пакетах нужно получить и вписать здесь
> после запуска у себя: в среде, где писался этот код, не было доступа к
> Maven Central, поэтому реальные запуски не выполнялись, а логика
> проверена модульными тестами на подставных POM-файлах.

## Правила оформления

В репозитории нет архивов, бинарных файлов и настроек редактора; код
соответствует лимитам (строки ≤ 80 символов, функции ≤ 40 строк,
цикломатическая сложность ≤ 10, аргументов ≤ 7), все функции имеют
docstring, числовые литералы в сравнениях вынесены в константы.
Проверка: `make check`. Сообщения коммитов следуют Conventional Commits.
